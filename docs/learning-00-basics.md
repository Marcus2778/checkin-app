# 第 0-1 课 为什么代码要分成"两半"

## 1. 你其实学过：C/S 模型

计算机网络里的 **C/S 模型（客户端-服务器模型，Client/Server）**，就是这个东西。本章只是把它落到一个具体项目上。

## 2. 偷懒实验：如果把整个应用都写成一个网页

假设我们把打卡应用**全放在用户手机里**，会发生什么？

| 问题 | 后果 |
|---|---|
| 用户按 F12 能看到**全部**代码 | 他看到了数据库地址和密码 |
| 用户能**改**自己手机上的代码 | 他把"判断任务是否完成"改成 `return true`，天天自动打卡 |
| 用户能直接连数据库 | 他可以改自己的记录，甚至读别人的 |

**结论：凡是"不能让用户看到、不能让用户改"的东西，都不能放在用户设备上。这就是前后端分工的唯一原因。**

## 3. 两半各自负责什么

```
┌──────────────────────────────┐        ┌──────────────────────────────┐
│   前端（Frontend）            │        │   后端（Backend）             │
│   跑在【用户手机/电脑】上       │        │   跑在【腾讯云服务器】上        │
├──────────────────────────────┤        ├──────────────────────────────┤
│ 画界面（按钮、文字、印章）      │        │ 存数据（数据库）               │
│ 响应用户点击                   │        │ 定规则（什么算打卡完成）         │
│ 把用户的意图「发消息」告诉后端   │        │ 定权限（你是谁、能改什么）       │
│ 把后端回的消息显示出来          │        │ 保管密码等敏感信息              │
├──────────────────────────────┤        ├──────────────────────────────┤
│ 反正全是公开的，看到也无所谓     │        │ 用户绝对碰不到                 │
│ 代码在 src/                   │        │ 代码在 backend/               │
└──────────────────────────────┘        └──────────────────────────────┘
              │                                       ▲
              │                                       │
              └───────────► 发消息 ◄──────────────────┘
                        （唯一的通道）
```

**对照项目：**

- `src/hooks/useAppData.ts`（前端）里 `api.toggleCheckin(...)` —— 意思是"**向后端发条消息**：我把这个任务勾上了"
- `backend/_lib/store.mjs`（后端）里判断"全部勾完了吗？勾完了就写一条记录" —— 这是**规则**，放在后端

**前端根本不知道"什么算打卡完成"这个规则**，它只是转发用户的动作。这条规则之所以安全，正是因为它不在用户手里。

## 4. 两半之间唯一的通道

前端**没有数据库地址，也没有密码**。它能做的只有一件事：

> **发消息给后端，等后端回话。**

这条"消息"就是 **HTTP 请求**（见第 0-2 课），后端回的那条叫 **HTTP 响应**。

# 第 0-2 课 一条 HTTP 消息长什么样

## 1. 用寄信来理解

| 信 | HTTP | 作用 |
|---|---|---|
| 收件地址 | **URL 路径** | 找谁 |
| 要办什么事（查询 / 提交） | **方法**（GET / POST） | 干什么 |
| 信封上的备注（"寄件人是张三"） | **请求头**（Headers） | 附带说明 |
| 信纸上的内容 | **请求体**（Body） | 真正的数据 |
| 对方回信第一句"办好了 / 你没资格" | **状态码** | 结果 |
| 回信的内容 | **响应体** | 返回的数据 |

**为什么"说明"和"内容"要分开？** 因为邮局（网络设备、服务器）**需要看信封才能决定怎么投递**，但**不需要拆开信**。所以"我是谁"（身份）写在信封上，"我要传的数据"写在信纸里。

## 2. 一条真实的请求（点勾选框时发的）

```http
POST /api/checkins HTTP/1.1              ← 第 1 行：方法 + 路径 + 协议版本
Host: 你的域名                            ← 以下全是「请求头」
Authorization: Bearer 7f3a9c...（64位）   ← 我是谁（登录凭证）
Content-Type: application/json            ← 我发的内容是 JSON 格式
Content-Length: 42                        ← 内容有 42 个字节
                                          ← 空行！头和内容的分界线
{"taskId":"3f8a1b2c","done":true}         ← 请求体（真正的数据）
```

- `POST` = **"我要写数据"**（不是只读）
- `/api/checkins` = 地址，后端拿它查"路由表"，找到 `checkins` 函数
- `Authorization: Bearer <token>` = **身份凭证**，后端靠它知道"你是谁"
- `Content-Type` = 告诉后端"我发的是 JSON"
- **空行** = 分界线，之前是"说明"，之后是"数据"

## 3. 一条真实的响应（后端回的）

```http
HTTP/1.1 200 OK                          ← 第 1 行：协议版本 + 状态码 + 简短说明
Content-Type: application/json           ← 以下全是「响应头」
Access-Control-Allow-Origin: *            ← 跨域许可

{"today":{"complete":true,...},...}       ← 响应体
```

## 4. 四个要素速查

| 要素 | 项目里的例子 | 说明 |
|---|---|---|
| **方法** | `GET` / `POST` | GET = 只读，POST = 要改数据 |
| **路径** | `/api/checkins` | 决定哪个函数处理 |
| **请求头** | `Authorization: Bearer xxx` | 身份等说明信息 |
| **请求体** | `{"taskId":"...","done":true}` | 真正的数据（GET 没有体） |

## 5. GET 和 POST

```
GET  /api/checkins     → 读：把今天状态、本周 7 天、连续天数给我
POST /api/checkins     → 写：我要把某个任务改成已完成
GET  /api/tasks        → 读：任务列表给我
POST /api/tasks        → 写：新建一个任务
```

**一条约定：GET 不应该改变服务器上的数据。** 除了"设计原则"这个理由，还有**实际的危险**——浏览器和中间的代理服务器**会缓存 GET 请求**，浏览器还会**提前预取**你可能会点的链接。如果 GET 有副作用，可能出现"用户根本没点，请求已经执行了"。

> 第一章 §1 里 `api/checkins/index.mjs` 用 `if (method === 'GET')` / `if (method === 'POST')` 分流——现在知道它在干什么了：**同一地址，读和写走不同分支。**

## 6. 状态码：后端回信的第一句话

项目里实际用到的全部：

| 状态码 | 含义 | 什么时候出现 |
|---|---|---|
| **200** | 成功 | 绝大多数正常返回 |
| **201** | 成功，并且新建了东西 | 新建任务成功（`api/tasks/index.mjs:36`） |
| **204** | 成功，但没什么可说的 | 浏览器的跨域预检请求（`http.mjs:37`） |
| **400** | 你发的东西有问题 | "任务不能为空"这类参数错误 |
| **401** | 你没登录 / 身份无效 | token 过期、密码错误 |
| **404** | 找不到 | 接口不存在、任务不存在 |
| **405** | 这个地址不支持这个方法 | 用 DELETE 调 `/api/checkins` |
| **409** | 冲突 | 用户名已被注册（`auth.mjs:73`） |
| **500** | 服务器自己出错了 | 代码抛了未预期的异常 |
| **503** | 服务暂时不可用 | 数据库连不上（`health.mjs:45`） |

**记法**：`2xx` 成功，`4xx` 是你的问题，`5xx` 是服务器的问题。

## 7. JSON：数据的写法

```json
{"taskId":"3f8a1b2c","done":true}
```

- 用 `{}` 包起来 = 一个对象，里面是 **键: 值**
- 键必须用双引号
- 值可以是文字、数字、真假、数组 `[]`、或再套一个对象

**用 SQL 知识类比：**

```sql
-- SQL 里的"一行记录"
taskId = '3f8a1b2c', done = true
```
```json
// JSON 里的"一个对象"
{"taskId":"3f8a1b2c","done":true}
```

**像，但不一样**：SQL 的行是"表里的一行"，有固定列；JSON 就是一段文字，想写什么写什么。所以项目里能把**整个任务数组**塞进一个 value：

```json
[{"id":"3f8a1b2c","title":"跑步 800 米","type":"daily","archived":false,"completedAt":null}]
```

这也是为什么 KV 存储只能存 JSON 字符串——**数据库那一列是 TEXT，只认文字**。

# 第 0-3 课 JavaScript 语法（一）：函数与箭头函数

> 全程**拿 C 语言对照讲**。

## 1. 函数：与 C 对比

```c
// C
int add(int a, int b) { return a + b; }
```

```js
// JavaScript
function add(a, b) { return a + b; }
```

**区别**：不用写 `int`。JS 是**动态类型**——变量不声明类型，运行时是什么就是什么。这是 JS 和 C 最大的区别，也是它灵活但容易出错的原因。

## 2. 箭头函数：只是"另一种写法"

```js
// 写法一：传统
function add(a, b) {
  return a + b;
}

// 写法二：箭头函数（更短）
const add = (a, b) => a + b;
```

规则：

```js
const f1 = (a, b) => a + b;              // 只有一行表达式 → 直接是结果，省略 {} 和 return
const f2 = (a, b) => { return a + b; };  // 加了 {} → 必须写 return
const f3 = (a) => a * 2;                 // 一个参数 → 括号可省：a => a * 2
const f4 = () => 42;                     // 没有参数 → 空括号
```

`=>` 念作"变成"，左边是输入，右边是输出。`f1` 读作"a 和 b 变成 a+b"。

## 3. 函数可以当参数传（关键）

**C 里**要把函数当参数传，得用**函数指针**，很啰嗦：

```c
int apply(int (*f)(int), int x) { return f(x); }
```

**JS 里**直接写就行——因为 JS 的函数本身就是个"值"，跟数字、字符串一样可以随便传：

```js
function apply(f, x) {
  return f(x);
}

apply((n) => n + 100, 5)   // 结果是 105
```

这里 `(n) => n + 100` 是个**没有名字的函数**（匿名函数），直接作为参数传进去。这种函数叫**回调函数**。

> **这是 JS 里最常见的模式，也是初学者最看不懂的地方。** 看到 `xxx((a) => ...)` 时，读法是：**"把箭头函数交给 xxx 去用"**。

## 4. 回到项目：最难看懂的那一行

`backend/api/checkins/index.mjs:11`：

```js
const handle = withHandler(async (context) => {
  const kv = getKV(context);
  // ...
});
```

**逐块拆：**

| 片段 | 含义 |
|---|---|
| `const handle =` | 定义一个叫 handle 的东西 |
| `withHandler(` | 调用 withHandler，**它的参数是一个函数** |
| `async (context) => { ... }` | 一个匿名函数：接收 `context`，函数体是那些大括号 |
| `)` | 结束调用 |

**整句读作**：

> "把 `async (context) => {...}` 这个函数**交给** withHandler 包装一下，包装后的结果存进 handle。"

`withHandler` 干了什么？看 `_lib/http.mjs:34`：

```js
export function withHandler(handler) {      // 接收一个函数当参数
  return async (context) => {               // 返回一个新函数
    if (context.request.method === 'OPTIONS') {
      return new Response(null, { status: 204, headers: JSON_HEADERS });
    }
    try {
      return await handler(context);        // 调用传进来的那个函数
    } catch (error) {
      // 统一处理错误
    }
  };
}
```

**它接收一个函数，返回一个新函数**——新函数在调用原来那个之前，先做点额外的事（处理跨域、兜住错误）。这个模式叫**包装**。

所以 `handle` 的完整等价写法是：

```js
const handle = async (context) => {
  if (context.request.method === 'OPTIONS') { ... }   // withHandler 加上的
  try {
    // ↓↓↓ 你写的业务逻辑
    const kv = getKV(context);
    const { username } = await requireUser(context, kv);
    // ...
  } catch (error) { ... }                             // withHandler 加上的
};
```

**为什么要这么写？** 5 个接口文件每个都要处理跨域、都要兜错误，写一遍就够了，不用抄 5 次。

```js
[1, 2, 3, 4, 5].filter((n) => n > 3)

// ④ 试着改成你要的
["跑步", "读书", "背单词"].map((t) => t + " 已完成")
```

**每行都把结果和你预期的对比一下。** 结果和预期不一样就停下来，先搞清那一行。

> 💡 Console 是学 JS 最好的工具——**即时反馈，不用配环境**。以后想验证任何 JS 写法，直接在这里试。

# 附录 A：本章纠正的三个常见误解

### ① 「路由表」：两个完全不同的东西撞了名字

| | 计网的路由表 | Web 后端的路由 |
|---|---|---|
| 在哪一层 | **网络层**（第 3 层） | **应用层**（第 7 层） |
| 住在哪 | 路由器/主机的**内核**里 | 服务器上的**一个程序**里 |
| 表里存什么 | 目的 IP 地址 → 下一跳地址 / 出口网卡 | URL 路径 → 一个**函数** |
| 决定什么 | 这个**数据包**往哪条线路发 | 这个**请求**交给哪段代码处理 |

**共同点**：都是"根据一个地址，决定下一步去哪"（`route` 本义是"路线"），所以两个领域各自借用了这个词。
**不同点**：一个转发**数据包**，一个调用**函数**，机制上毫无关系。

> 💡 学习方法：**计算机里很多词在不同层次被重复使用**（地址、端口、路由、缓存、协议…）。每次看到熟悉的词，先问一句"**现在说的是哪一层？**"——八成是另一个东西。

### ② 「前端做了限制」≠「有约束」

前端把按钮藏起来、加 `disabled`、改校验逻辑——**全都不构成约束**。用户能改前端代码，也能完全绕过前端直接发请求。

### ③ GET 不能改数据：不只是"约定"

除了设计原则，还有实际的坑：**GET 会被缓存、会被预取**，有副作用就会出事。

# 附录 B：本章新增术语速查

| 术语 | 通俗解释 |
|---|---|
| **C/S 模型** | 客户端-服务器模型：一半代码在用户设备上，一半在服务器上 |
| **HTTP 请求 / 响应** | 前端发给后端的一条消息 / 后端回的一条消息 |
| **方法（GET/POST）** | 这条消息是"要读"还是"要写" |
| **请求头 / 响应头** | 消息的"信封"，放身份、格式等说明信息，不放业务数据 |
| **请求体 / 响应体** | 消息的"信纸"，放真正的数据 |
| **状态码** | 后端回信的第一句话：2xx 成功，4xx 你的问题，5xx 服务器的问题 |
| **JSON** | 一种用纯文字表示数据的格式，长得像对象。数据库里存的就是 JSON 字符串 |
| **箭头函数** | `(a) => a + 1` 这种简写的函数 |
| **匿名函数 / 回调函数** | 没有名字、直接当参数传给别的函数的函数 |
| **包装** | 接收一个函数、返回一个新函数，在新函数里做额外的事（如 `withHandler`） |
| **F12 / 开发者工具** | 浏览器自带的调试面板，能看网络请求、改页面、跑 JS |
| **Console 控制台** | F12 里的一个标签，可以当场输入 JS 并立即看到结果 |
| **curl** | 命令行发 HTTP 请求的工具（Windows 上要写 `curl.exe`） |
| **Local Storage** | 浏览器给每个网站的一小块本地存储空间，项目里用它存登录 token |
