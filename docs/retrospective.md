3. 作为计算机专业的学生，这里有哪些值得学的知识

## 0. 先说结论：时间到底花在哪了

| 阶段 | 大致占比 | 说明 |
|---|---|---|
| 讨论需求、定方案 | ~10% | 值得，省掉了后面返工 |
| 写本地能跑的完整应用 | ~25% | 前端 + 后端 + 99 个测试 |
| 界面返工（你说"AI 感太重"） | ~10% | 换成盖章设计 |
| **部署上线** | **~55%** | ← **就是这里** |

**「部署」这一半时间，几乎全花在腾讯云上，而且经历了两次推倒重来。**

### 一句话原因

> **写代码是「逻辑问题」，部署是「环境问题」。逻辑问题可以推理，环境问题只能撞。**

具体来说，你遇到的不是"我写错了代码"，而是这些：

- 某个功能**在文档里没写要审批**，写完才发现要审批（EdgeOne 的 KV 存储）
- 某个域名**看起来能用**，实际从中国大陆访问直接返回 401（地域限制）
- 某个工具**在你本机跑得通**，到了云端换了一套加载规则（CommonJS / ESM）
- 某个配置**默认值是错的**，但只有真正跑起来才会暴露（路径透传、数据库 schema）

这些东西有个共同点：**没有报错信息告诉你"你错在哪"，只有一个笼统的失败。**
比如 `0 code exit unexpected`（进程意外退出）——它没说是模块加载失败、还是依赖没装、还是别的。

### 还有个更根本的原因：我的顺序错了

我一开始的做法是：**先写完一整套后端，再去部署**。

结果 EdgeOne 那条路走到最后才发现它的存储功能根本批不下来——**整套后端白写了**。

正确的顺序应该是：**先花 20 分钟验证平台能不能用，再动手写代码。**
后来我改成这个做法，CloudBase 一次就过了可行性验证。这个教训写在后面第 5 节。

## 1. 这个项目是什么

### 架构图

```
┌─────────────────────────────────────────┐
│  浏览器（你的手机 / 电脑）                  │
│  React 单页应用，跑在用户设备上              │
└────────────────┬────────────────────────┘
                 │  HTTPS 请求，形如 GET /api/checkins
                 │  带上 Authorization: Bearer <登录凭证>
                 ▼
┌─────────────────────────────────────────┐
│  CloudBase 网关（平台提供的入口）           │
│  按路径分发：/ 给网页，/api/* 给后端函数     │
└────────────────┬────────────────────────┘
                 ▼
┌─────────────────────────────────────────┐
│  云函数 api（我们写的后端，跑在腾讯云）       │
│  ┌───────────────────────────────────┐  │
│  │ 适配层：把平台的事件翻译成标准请求/响应  │  │
│  ├───────────────────────────────────┤  │
│  │ 路由表：这个路径该交给哪个函数处理      │  │
│  ├───────────────────────────────────┤  │
│  │ 业务逻辑：任务、打卡、连续天数、登录     │  │
│  ├───────────────────────────────────┤  │
│  │ 存储抽象层（kv.mjs）：只管增删改查      │  │
│  └──────────────┬────────────────────┘  │
└─────────────────┼───────────────────────┘
                  ▼
┌─────────────────────────────────────────┐
│  PostgreSQL 数据库（腾讯云托管）            │
│  一张表：kv(key, value)                   │
└─────────────────────────────────────────┘
```

### 一次「打卡」的完整旅程

你在手机上点一下任务前面的方框，背后发生的事：

1. 前端乐观更新——**界面上立刻盖上章**，不等服务器（不然要等 300 毫秒才响应，手感很差）
2. 同时发一个请求：`POST /api/checkins`，body 是 `{ taskId: "xxx", done: true }`
3. 请求到达 CloudBase 的网关，网关发现路径以 `/api/` 开头，转给我们写的云函数
4. 云函数**先把网关给的"事件"翻译成标准的 Web Request 对象**
5. 路由表发现 `/api/checkins` 对应 `api/checkins/index.mjs`
6. 那个文件先验证你的登录凭证（去数据库查 `session_<token>`）
7. 通过后进入业务逻辑：把任务标记为完成 → 判断"今天是不是全部做完了"
8. 如果全做完了，**写入一条 `rec_<用户名>_<日期>` 记录**——这一条就是"这天打过卡"的凭证
9. 重新计算连续天数，把结果返回给前端
10. 前端拿到服务器返回的真实状态，覆盖掉刚才的乐观更新

**关键设计在第 8 步**：`rec_` 记录只在"当天全部完成"时才存在。
于是"这个人哪些天打过卡" = 去数据库里按前缀查一下有哪些 key。
**不需要读取任何一条记录的内容**，连续天数直接从这个日期列表算出来。

## 2. 为什么这么慢：三个真正的原因

### 原因一：平台的能力边界是不透明的

你想要的"国内朋友不用梯子就能访问"，这个需求把可选平台砍掉了一大半。我们依次试过/排除过：

| 平台 | 为什么不行 |
|---|---|
| Netlify、Vercel | 国内访问不稳定，经常打不开 |
| Cloudflare Pages | 联通晚高峰很差 |
| 阿里云 OSS、腾讯云 COS | 只有静态文件，跑不了后端；而且必须备案 |
| LeanCloud | 2027 年停服 |
| Supabase | 国内没有节点 |
| **EdgeOne Pages** | **看着最合适，实际有两个致命问题（见下）** |
| **CloudBase** | 最终采用 |

**EdgeOne 的两个致命问题**，都是"写代码前查不到、写完才知道"的类型：

1. **它的 KV 存储（存数据的功能）处于内测阶段，要白名单审批。**
   文档里只在角落提了一句"面向企业版套餐"。我让你提交了申请，
   状态在"审核中"和"未开通"之间反复。**没有这个功能，整个后端存不了任何数据。**

   > 这里有个术语：**KV 存储** = Key-Value 存储，一种最简单的数据库，
   > 给它一个"钥匙"（key），它返回对应的"东西"（value）。
   > 我们的 `user_alice` → `{密码哈希...}` 就是这样存的。

2. **它的默认域名从中国大陆访问直接返回 401（无权限）。**
   官方文档写着：全球可用区（不含中国大陆）的项目，"中国大陆网络环境将返回 401 错误"。

   > **域名** = 网址里 `https://` 后面那串，比如 `checkin-app.edgeone.cool`。
   > **默认域名** = 平台免费送你的域名，不用自己买。

   **最坑的是**：这个问题一度被掩盖了。因为你的电脑上开着代理软件（Hiddify），
   流量从境外绕了一圈出去，EdgeOne 以为你是海外用户，就正常返回了。
   我一度得出"国内直连没问题"的**错误结论**——关掉代理才暴露出来。

   > 这件事值得单独记一笔：**开着梯子测"国内能不能访问"，测的是梯子，不是你的网站。**

### 原因二：云端的运行规则和你本机不一样

这是我踩的最隐蔽的一类坑。同样一份代码：

- **在你自己电脑上**：用 `import` / `export`（ES 模块语法）没问题
- **到了 CloudBase 云函数里**：只能用 `require` / `exports`（CommonJS 语法），
  用 ES 模块语法会**直接崩溃**，而且报错信息是 `0 code exit unexpected`——
  完全看不出是语法问题

> **ES 模块 / CommonJS** = JavaScript 两种"把代码拆成多个文件再互相引用"的写法。
> 前者是新的（`import x from './y.js'`），后者是老的（`const x = require('./y')`）。
> 你本机装的 Node.js 24 两种都支持，但云平台**只认老的那种**。

**为什么这个特别难查**：因为报错完全指不到原因。我是靠"写一个什么都不做、
只返回一句话的最简函数，发现它也崩"才定位到的——**用排除法把变量一个个减掉**。
这在排查里叫**二分定位**，是很有用的技能。

### 原因三：验证工具本身受限制

部署出问题的时候，最需要的是**看日志**。但：

- CloudBase 的日志服务在这个环境里没开（报 `topic not exist`）
- 我用命令行发请求，网关又会把非浏览器的请求挡掉

**所以我当时是"瞎的"**——只能靠把错误信息塞进接口返回值里、
或者写一个专门用来"吐信息"的临时函数，才能看到发生了什么。

这解释了一个你可能觉得奇怪的现象：为什么我一会儿让你去控制台点一下、
一会儿又自己跑命令行。**因为有些事我真的做不了**——
我能执行命令，但看不见你的屏幕，也点不了浏览器里的按钮。

## 3. 值得学的知识（按你说的，部署部分最详细）

### 3.1 部署与运维 ← 你说的大头

这部分最"不像编程"，但**工作中最常遇到**，而且学校里基本不教。

#### (1) 一个网站上线，到底需要几样东西？

| 东西 | 是什么 | 我们的选择 |
|---|---|---|
| **域名** | 网址的名字 | 平台白送的（代价是它会弹提示页） |
| **服务器 / 运行环境** | 跑代码的地方 | CloudBase 云函数 |
| **数据库** | 存数据的地方 | CloudBase 的 PostgreSQL |
| **HTTPS 证书** | 让网址是 `https://` 而不是 `http://` | 平台自动配，不用管 |
| **备案** | 中国的行政要求（见下） | 没做，所以走的是境外节点 |

#### (2) 什么是「云函数」和「无服务器」

你可能会想：为什么不租一台服务器，把代码放上去跑？

**云函数（Serverless / 无服务器）**是另一种模式：

- 你不用管服务器，**只上传一个函数**，平台负责运行它
- 没人访问时**它不占资源，也不收钱**（或很便宜）
- 有人访问时才启动，用完就回收

代价是：

- **冷启动**：太久没人访问，第一个请求会慢一点（要先把运行环境启起来）
- **限制多**：我们的云函数不能装任意依赖、有超时限制、**而且只认 CommonJS**
- **调试难**：本地跑得好好的，云端可能因为环境不同而挂

> **为什么这个项目适合云函数**：打卡应用一天可能就几十次请求，
> 租一台服务器 24 小时开着是浪费。云函数按用量计费，用多少算多少。

#### (3) 什么是「网关」和「路由」

用户访问 `https://xxx.com/api/checkins`，这个请求**怎么知道该交给谁处理**？

**网关**就是门口的分诊台：

```
/                 → 交给静态网页（前端）
/api/health       → 交给云函数 api
/api/auth/login   → 交给云函数 api
/api/tasks        → 交给云函数 api
...
```

**这里踩了个大坑**（README 里的「坑 2」）：

网关有个设置叫 `enablePathTransmission`（**路径透传**），默认是**关**的。
关着的时候，它只把"匹配之后剩下的路径"传给后端。

结果就是：配了 `/api/health` 这条路由，**后端收到的路径变成了 `/`**——
它以为自己被访问的是首页，于是所有接口都报"没有这个接口"。

**这类坑的教训**：配置项的**默认值**往往是最容易出事的地方，
因为你不看它、它却在悄悄影响行为。

#### (4) 数据库的「角色」和「权限」

**这是最值得学的一块，也是最容易埋安全隐患的地方。**

数据库不是"连上了就什么都能干"。它有一套**角色（role）**系统，
每个角色有不同的权限。我们的表上长这样：

| 角色 | 权限 | 谁在用 |
|---|---|---|
| `anon`（匿名） | **只能读** | 云函数最初拿到的身份 |
| `authenticated`（已登录用户） | 全部 | — |
| `service_role`（服务端） | 全部 | 应该用它 |

**问题的根源**：SDK 拿到的凭据映射到了 `anon`，所以**读得了、写不了**，
报 `permission denied for table kv`（表 kv 权限不足）。

**我是怎么解决的**：建了一个 CloudBase API Key，让云函数用它，
这样就以**服务端身份**访问数据库。

**为什么没走"直接给 anon 开写权限"这条捷径**：

> 那等于把整张表的读写权限开放给所有持有"匿名凭据"的人。
> 而我们的表里存着**所有人的密码哈希**——虽然哈希不能直接反推出密码，
> 但让陌生人能读能写你的用户表，是绝对不该做的事。

**这条经验请记住**：

> **遇到权限报错时，正确做法是「让程序用应有的身份」，
> 而不是「把权限放大到能让当前身份通过」。**

#### (5) 什么是「备案」，为什么绕不过去

**ICP 备案**：中国大陆的行政法规——**在国内提供互联网信息服务，必须登记**。

对你的影响：

| 情况 | 备案 | 速度 | 能不能用 |
|---|---|---|---|
| 用平台的默认域名 | 不用 | 快 | 能，但会弹"测试域名"提示页 |
| 绑定自己的域名，走**国内节点** | **必须** | 最快 | 能 |
| 绑定自己的域名，走**境外节点** | 不用 | 慢一点（~200ms） | 能 |

**这不是技术问题，是法规问题**，任何平台都绕不过去。
想彻底去掉那个提示页，就必须：买域名 → 实名认证 → 提交备案（约 1-3 周）→ 绑定。

#### (6) 环境变量与密钥管理

云函数需要一把"钥匙"去访问数据库。这钥匙**不能写在代码里**，
因为代码要提交到 GitHub，**全世界都能看到**。

做法是**环境变量**：

```json
// cloudbaserc.json —— 提交到仓库的是这个模板，不是真钥匙
"envVariables": {
  "CLOUDBASE_APIKEY": "{{env.CHECKIN_APIKEY}}"
}
```

`{{env.CHECKIN_APIKEY}}` 是个**占位符**，部署的时候才从你本机的环境变量里取值填进去。
**真钥匙永远不进仓库、不落盘。**

> **为什么这个重要**：GitHub 上每天都有人的密钥被泄露，然后被人拿去挖矿。
> 有一个专门的词叫 "secret scanning"（密钥扫描），GitHub 会自动扫描公开仓库里的密钥格式。
> **习惯是：凡是要连数据库、调第三方 API 的密钥，一律走环境变量。**

### 3.2 后端知识

#### (1) HTTP 是有"语义"的

不是"能传数据就行"。每个请求方法、每个状态码都有约定含义：

| 方法 | 含义 | 我们用在 |
|---|---|---|
| GET | **读取**，不该改变任何数据 | 查任务列表 |
| POST | **创建**新东西 | 注册、新建任务、打卡 |
| PATCH | **部分修改**已有东西 | 改任务标题 |
| DELETE | **删除** | 删任务 |

| 状态码 | 含义 | 什么时候用 |
|---|---|---|
| 200 | 成功 | 正常返回 |
| 201 | **创建成功** | 注册成功时（不是 200） |
| 400 | **你发来的请求有问题** | 用户名含非法字符 |
| 401 | **你没登录 / 登录失效** | token 不对 |
| 404 | **没有这个东西** | 访问不存在的接口 |
| 409 | **冲突** | 用户名已被注册 |
| 500 | **我的服务器出错了** | 数据库连不上 |

**为什么较真这个**：400 和 500 的区分，决定了出问题时是"你改"还是"我改"。
我们把"用户名重复"返回 409 而不是 500，就是在说"这是你的输入问题，不是我的故障"。

#### (2) 密码绝对不能明文存

这是后端最重要的常识。我们的做法：

1. **加盐（salt）**：给每个用户生成一段随机字符串，和密码拼在一起再哈希。
   > **为什么**：不加盐的话，两个用同样密码的人，哈希值会一模一样；
   > 而且攻击者可以拿一张"常见密码 → 哈希值"的对照表（叫彩虹表）直接反查。
   > 加了盐，每个人的哈希都不同，对照表就失效了。

2. **用慢函数**：PBKDF2，迭代 30 万次。
   > **为什么故意要慢**：正常的哈希（比如 MD5）快到可以每秒试几十亿次。
   > 密码哈希要慢到"每次尝试 30 毫秒"，这样暴力破解的成本就高到不划算。
   > **这是一个"故意降低性能来换安全"的设计**，很少见，值得记住。

3. **恒定时间比较**：验证密码时，不能"发现第一个字符不对就立刻返回"。
   > **为什么**：那样攻击者能通过"响应时间的长短"一个字符一个字符地猜出正确值。
   > 这叫**时序攻击（timing attack）**。代码里为此专门写了个函数，
   > 无论对错都要比完全程。

#### (3) 时区：一个几乎人人都会踩的坑

**云服务器的时钟默认是 UTC（世界标准时间），不是北京时间。**

不处理的话：**晚上 8 点之后打的卡，会被记到第二天**。
（因为北京时间 20:00 = UTC 12:00，而 UTC 日期可能还是前一天……具体取决于时刻。）

我们的做法：所有日期都经过 `date.mjs` 转成北京时间再算。

> **这条经验适用于任何服务器项目**：只要涉及"今天""昨天"，
> 就必须明确"谁的今天"。永远不要让服务器用默认时区算日期。

#### (4) 数据建模：一个好设计能省掉很多代码

回到那个 `rec_` 记录的设计：

**笨办法**：存一张"打卡记录表"，每天一行，记录完成了几个任务。
算连续天数时，把所有记录读出来，排序，遍历，找最长的连续段。

**我们的办法**：**只在"当天全部完成"时写入一条记录**。
于是"哪些天打过卡" = 按前缀查一下 key 列表。

**好处**：
- 算连续天数**不需要读任何记录的内容**，只需要知道 key 的名字
- 存储量更小（没完成的日子不存）
- 逻辑更简单（不存在"完成了 80% 算不算"的模糊地带）

**这类思考叫「按查询需求设计存储」**——先想清楚"我要怎么查"，
再决定"怎么存"。而不是先建一张看起来很规范的表，再想办法查。

### 3.3 前端知识

#### (1) 「乐观更新」——为什么点一下就有反应

按传统做法：点击 → 发请求 → 等服务器返回 → 更新界面。
问题是服务器在腾讯云，一来一回可能要 **300 毫秒**——手感会很迟钝。

**乐观更新**是：**假设请求会成功，先更新界面**，等服务器真的返回了再校正。

> 名字里的"乐观"就是这个意思：**乐观地认为不会失败**。
> 失败了怎么办？把界面回滚。我们的代码里保留了一份"服务器真实状态"，
> 乐观状态只在请求进行期间生效。

#### (2) React 里的「派生状态」

界面上要显示"今天完成了几项"，这个数字**不需要单独用一个变量存**。

因为它是**从已有数据算出来的**：

```js
const doneToday = todoTasks.filter(t => doneIds.has(t.id)).length
```

**为什么不单独存**：如果单独存一个 `doneCount` 变量，
你必须记得在**每一个**可能改变它的地方同步更新。漏掉一处，界面就显示错的数字。
**从源头算出来，就永远不会不同步。**

> 这是 React 里非常重要的一条原则：**能算出来的，就不要存。**

#### (3) 无障碍（a11y）：为什么代码里有 `aria-label`

我们的任务勾选框在视觉上是个"印章"，里面没有文字。但屏幕阅读器（给视障用户用）
读到它时，需要知道"这是哪个任务"。

所以代码里写了：

```jsx
<input type="checkbox" className="sr-only" aria-label={task.title} />
```

`aria-label` 就是给屏幕阅读器听的标签。`sr-only` 意思是"只在屏幕阅读器里可见"——
视觉上隐藏（因为我们要显示自定义的印章），但对辅助技术保留。

> **为什么值得学**：这是"代码质量"里最容易被忽略、
> 但在真实工作中会被要求的一部分。而且它成本很低——加个属性而已。

#### (4) CSS：用 SVG 滤镜"揉歪"印章

你说过第一版"AI 感太重"。改造的核心是**让完成标记看起来像真的盖上去的章**，
而不是一个方方正正的色块。

做法是用 SVG 滤镜：

- `feTurbulence`：生成噪声（可以想象成"随机扰动场"）
- `feDisplacementMap`：用噪声**把图形的边缘推歪**
- 第二层噪声调制墨色的浓淡

结果是每枚章**边缘都是不规则的**，而且**每枚都不一样**（用日期做种子，
所以同一个日期每次渲染都一样，不会闪烁）。

> **值得学的点**：这不是"调 CSS 属性"，而是**用图形算法做出质感**。
> 而且这个决定背后有个判断：**"完美"是机器最容易产出的东西，
> "不完美"才是最难的**——所以刻意做不完美，反而有了人味。

### 3.4 工程习惯

#### (1) 抽象层：为什么换平台只改了一个文件

`kv.mjs` 定义了一套"存储接口"：`get / put / delete / list`。

- 业务代码（`store.mjs`、`auth.mjs`）**只调这 4 个方法**，不知道底层是什么
- 本地开发时，底层是内存实现（`mock-kv.js`）
- 线上跑时，底层是 PostgreSQL 实现（`kv-cloudbase.mjs`）

**结果**：从 EdgeOne 换到 CloudBase 时，**换掉的是底下那一层，
上面的业务逻辑一行没改**。

> 这叫**依赖倒置**或者说**面向接口编程**。
> 收益在"变化发生时"才体现出来——写的时候多花一点心思，改的时候省几小时。

#### (2) 测试分三层

| 层 | 测什么 | 例子 |
|---|---|---|
| 纯函数 | 不依赖任何外部东西的逻辑 | 连续天数计算的各种边界情况 |
| 接口 | 完整的 HTTP 流程 | 注册 → 登录 → 打卡 → 查统计 |
| 平台适配 | 平台特有的翻译逻辑 | 事件 → Request 的转换 |

**为什么分层**：纯函数测试跑得飞快（99 个测试 1.2 秒），能覆盖大量逻辑；
平台适配层最危险（最容易出错又最难查），所以单独测。

**这次测试真的救了命**：迁移时有个测试断言"路由表和 `api/` 目录必须完全一致"——
它防的是"加了新接口但忘了在路由表里注册"。
这种错误在本地开发时**完全正常**（本地是按文件路径找的），只有线上会 404。

还有一个测试发现了**真实的安全缺陷**：客户端发来的登录凭证
被直接拼进了数据库的 key 里，导致发送畸形凭证会返回 500 而不是 401。
这个 bug 一直存在，是写新测试时才被逮到的。

#### (3) 用「契约」让 mock 和真实实现保持一致

`dev/mock-kv.js`（内存版）和 `kv-cloudbase.mjs`（真实版）实现**同一套接口**。
它们的"契约"是：`get` 返回字符串或 null，`list` 返回 `{ keys, cursor, complete }`。

所以本地开发时跑出来的行为，就是线上的行为。
**不需要先注册云服务，就能把整个应用跑起来。**

> 这一点对你特别有用：**想改界面、加功能时，直接 `npm run dev:mock` 就行**，
> 不碰任何云服务，秒级启动。

## 4. 完整工作流：从零到上线

这是这个项目实际走过的路，也是**任何 Web 项目都适用的流程**：

```
① 讨论需求，定方案
   ↓  你明确说了"先讨论方案，确定细节再做"——这一步省掉了大量返工
② 选技术栈
   ↓  前端 React + TypeScript，后端云函数 + 数据库
③ 【关键】本地开发环境先跑起来
   ↓  写一个内存版后端，不需要任何云服务账号
④ 写后端：先地基（工具函数）再楼房（业务逻辑）
   ↓  时区转换 → 连续天数（纯函数，带测试）→ 登录认证 → 业务接口
⑤ 写前端：先骨架再细节
   ↓  登录页 → 主页面 → 逐个组件
⑥ 用真实浏览器验证界面
   ↓  截图看效果，发现"AI 感太重" → 重做设计
⑦ 【关键】验证平台可行性
   ↓  这一步我做晚了，应该是第 ② 步之后就做
⑧ 部署：静态网页 + 云函数 + 数据库 + 网关路由
   ↓  踩了 4 个平台坑
⑨ 端到端验证
   ↓  命令行验证 + 真实浏览器验证 + 手机流量验证
```

### 第 ③ 步值得单独讲：为什么先做"内存版后端"

如果一开始就要连真实的云数据库，你会遇到：

- 改一行代码要重新部署（几十秒）
- 数据库连不上时，分不清是代码问题还是网络问题
- 没法自动化测试（测试需要真数据库）

**内存版后端**把"存储"换成一个内存里的字典，其他全是真的。
于是：

- 改代码**立刻生效**（热更新）
- 测试**毫秒级**跑完
- 团队新人拉下代码 `npm install && npm run dev:mock` **就能跑**

**代价**：需要多写一个 mock 实现（我们的约 60 行）。
**收益**：整个开发过程快了好几倍。

## 5. 如果重来一次，怎么更快

按重要性排序：

1. **先验证平台，再写代码。**
   花 20 分钟跑通一个"最简全链路"（能显示网页 + 能读写数据库的一条记录），
   再动手写业务。这一步能提前暴露 80% 的平台坑。

2. **测试"能访问"时，一定要在真实条件下测。**
   开着代理测"国内能否访问" = 没测。
   **关掉代理 + 用手机流量**，这才是真实条件。

3. **遇到平台报错时，先写一个"什么都不做"的最简版本。**
   如果最简版本都失败，问题一定在平台配置，不在你的代码。
   这能把排查范围瞬间砍掉一半。

4. **看懂报错比猜有用。** 但平台报错常常很笼统——
   这时候要想办法"让它多说点"：把错误信息写进接口返回值、
   写个专门吐信息的临时函数、看日志。**不要靠猜。**

5. **优先用平台的"标准做法"，不要自创。**
   我们最初用 ES 模块（更现代），结果平台只认 CommonJS。
   跟平台较劲通常是浪费时间——除非你有明确理由。

## 6. 术语表

把我说过、但你可能不好意思问的词都列在这。

| 词 | 白话解释 |
|---|---|
| **前端 / 后端** | 前端 = 在用户设备上跑的代码（看得见的部分）；后端 = 在服务器上跑的代码（看不见的部分） |
| **API** | 前端和后端之间的"约定"：我按这个格式问你，你按那个格式答我 |
| **云函数 / Serverless** | 只上传一个函数，平台负责运行，不用管服务器，按调用次数计费 |
| **边缘函数** | 云函数的一种，跑在离用户更近的节点上，更快但限制更多 |
| **冷启动** | 函数太久没被调用，下次调用时要先启动环境，会慢一点 |
| **网关 / 路由** | 门口的"分诊台"，决定一个请求该交给谁处理 |
| **域名** | 网址里 `https://` 后面那串字 |
| **CDN** | 把网页文件复制到各地的服务器上，让用户从最近的拿，更快 |
| **KV 存储** | 最简单的数据库：给个"钥匙"，返回对应的"东西" |
| **关系型数据库 / PostgreSQL** | 用表格存数据的数据库，能表达"这两个表有关系" |
| **schema** | 数据库里的"命名空间"，用来给表分组。默认的叫 `public` |
| **角色 / 权限** | 数据库里"谁能干什么"的规定 |
| **环境变量** | 不写在代码里、由运行环境注入的配置，常用来放密钥 |
| **密钥 / API Key** | 程序的"身份证 + 钥匙"，证明"我是有权限的那个程序" |
| **PBKDF2 / 哈希** | 把密码变成一串不可逆的乱码，用来存密码（不能明文存） |
| **加盐 / salt** | 哈希之前先掺一段随机字符串，防止两个相同密码哈希值相同 |
| **token / 会话** | 登录成功后服务器给你的"临时通行证"，之后每次请求带上它 |
| **HTTP 状态码** | 服务器回应里的数字：200 成功、400 你请求有问题、401 没登录、500 我出错了 |
| **CORS** | 浏览器的安全策略，限制网页能不能跨域名请求别家接口 |
| **UTC / 时区** | 世界统一时间。服务器默认用它，所以算"今天"要手动转成北京时间 |
| **ICP 备案** | 中国的行政法规：在国内提供网站服务必须登记 |
| **乐观更新** | 先改界面、再等服务器确认，让操作手感更快 |
| **mock** | 假实现，用来在没接真实服务时开发 |
| **重构** | 不改功能，只改代码结构，让它更好维护 |
| **ES 模块 / CommonJS** | JavaScript 两种"模块化"写法，新的和老的 |
| **TypeScript** | 给 JavaScript 加上"类型检查"，能在写代码时就发现错误 |

## 7. 下一步可以学什么

按"投入产出比"排序：

1. **把这套东西自己重写一遍。** 不看我的代码，从 `npm create vite` 开始，
   凭理解搭出前端 + 一个最简单的接口。**卡住了再回来看。**
   这是最有效的学习方式。

2. **加一个功能，走完整流程。** 比如"完成任务可以写一句备注"：
   改数据库结构 → 改后端接口 → 改前端界面 → 加测试 → 重新部署。
   走一遍你就真正掌握这个工作流了。

3. **打开浏览器的开发者工具（F12）看 Network 面板**，
   自己点几下应用，看它发了哪些请求、返回了什么。
   **把"看到的现象"和"背后的请求"对上号**，是前端进阶的关键一步。

4. **学 Git 的分支。** 现在你只会"提交到主分支"。
   真实工作中每个人开一个分支，写完再合并（Pull Request）。
   试着开个分支改点东西，再合并回来。

5. **补计算机基础课和实际的对应关系**：
   - 操作系统 → 进程、内存、文件系统（云函数就是被管起来的进程）
   - 计算机网络 → HTTP、TCP、DNS（你这次的每个坑几乎都是网络问题）
   - 数据库 → 索引、事务、范式（我们那张 `kv` 表的 key 是主键，所以查得快）
   - 信息安全 → 哈希、加盐、时序攻击、权限最小化

**最后一句**：你这次遇到的**全是真实工作中会遇到的典型问题**——
地域限制、平台能力边界、权限模型、密钥管理、时区、跨平台兼容。
很多人工作一两年才会把这些碰全。**这不是"运气差"，这是真实的工程。**
